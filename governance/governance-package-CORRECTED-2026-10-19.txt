THE PROBLEM
Sammy's prompts, memory, and working rules live scattered
across roughly a hundred saved copies on platforms that make
saving and getting back OUT hard. Copies drift: summaries and
regenerations come back changed, and an engineer working from
a drifted copy builds the wrong thing. There is no single
book that holds the record and can be checked.
THE PRODUCT IN ONE LINE
Our Notebook is a source-grounded research assistant: a
notebook that holds Sammy's three types of prompt —
1. Memory (about Sammy and his challenges; shared among the
   builders),
2. Quality Of Work (the standards every engineer adheres to),
3. Project Specific —
and lets the crew read, sort, file, and answer FROM the book,
so answers are grounded in what is actually written there
instead of in what an AI half-remembers.
The book holds the record. The book never does the job.
The work happens at the engineers' own benches.
USERS
- Sammy Reed — founder, owner, and the only bridge between
  the engineers.
- The Crew — Muse (Builder / Record Keeper), Gemini
  (Research And Development / Clerical), DeepSeek (Final
  Auditor), ChatGPT (Builder). Each AI works in its own lane;
  nobody audits their own work.
SCOPE — THE TEST CUT
- One self-contained HTML file. No accounts, no sign-in, no
  cloud, no external scripts, fonts, images, or network
  calls of any kind.
- Opens with three notebooks: Ideas & Inspiration · Sammy ·
  Muse — Record Keeper.
- Create, rename, and delete notebooks; create, edit, and
  delete notes.
- Autosave to the browser's local storage on the device,
  as the user types.
- One search box that searches across ALL notebooks.
- Export the current notebook as .txt; export everything as
  one .json; import a .json to restore.
- The word PROTOTYPE stays visible in the header at all
  times.
- Big buttons and big text — used on a phone, by big fingers.
- The benchmark build already exists (built 2026-10-18);
  this charter governs the test cut and every build after it.
NON-GOALS — WHAT THIS IS NOT
- NOT a NotebookLM clone. Public functionality inspired the
  idea; no NotebookLM user interface, wording, icons,
  prompts, datasets, color scheme, or trade dress is copied.
- NOT for resale. Built for Sammy personally and the Opal
  fleet, under his own declared paper trail.
- NOT a finished product. Internal controlled prototype
  first; no public launch under this charter.
- NOT a place for secrets. There is deliberately no field
  for an API key, password, or token anywhere in it.
- NOT shared by default. Memory marked NOT SHARED stays
  locked; types 1 and 2 are shared among the builders only
  as the founder directs.
SUCCESS TEST
The Six-Test Score Sheet (see tests/acceptance-tests.txt).
Pass or fail, no middle:
1. MAKE  2. SURVIVE  3. FIND  4. LEAVE  5. RETURN  6. ALONE
All six pass = the build method is proven for the next apps.
Fail SURVIVE or RETURN = it is not a notebook, it is a trap.
Fail ALONE = record which step needed the network.

SECURITY BASELINE
================================================================
SECURITY BASELINE — MASTER BLUEPRINT GOVERNANCE PACKAGE
Project: Our Notebook, First Test Cut
Opened: 2026-10-19
Posture: PROTOTYPE — local only. This baseline covers the
prototype. Production controls get their own review at the

================================================================
DATA FLOW — ONE PAGE, WHOLE TRUTH
1. Sammy types in the app, in a browser, on his own device
   (iPhone or Chromebook).
2. The app saves what he types to the browser's local
   storage, on that same device, under one key
   (ourNotebookV1). Nothing leaves the device.
3. Export: the app hands the browser a file to download —
   the current notebook as .txt, or everything as .json.
   The file lands wherever Sammy saves it.
4. Import: Sammy picks a .json file; the app reads it and
   restores what it holds.
5. The crew sees notebook content only when Sammy carries
   it to them himself. Sammy is the only bridge. There is
   no sync, no account, no server, no network call of any
   kind — Test 6 (ALONE) in the score sheet proves it with
   the network off.
WHAT DOES NOT EXIST IN THIS BUILD
- No accounts and no sign-in.
- No cloud storage and no external saving.
- No analytics, no tracking, no telemetry.
- No field for an API key, password, or token — by design.
THE SECRETS RULE — HOUSE LAW, RESTATED
- The vault holds the values: Bitwarden, browser storage,
  or Google Keep. Muse holds the MAP — which keys exist
  and where they live — and never the values.
- Keys, tokens, and passwords never go inside notes,
  prompts, shortcuts, code, or this notebook.
- A key is a wallet. Code gets copied everywhere a file
  goes; a secret in code is a secret published.
KNOWN LIMITS — STATED PLAINLY (from Audit Package v1)
- Local storage is per-browser, per-device: notes do not
  sync between the phone and the Chromebook. Exports are
  the bridge.
- Browser storage can be cleared by the browser or the
  operating system. The app tells the user to export
  copies; the copies are the protection.
- No encryption at rest. Nothing secret belongs in this
  notebook — that is rule, not oversight.
BACKUPS AND RESTORE
- The Four Copies Rule governs project files: 1 ORIGINAL
  (untouched) · 2 MASTER · 3 DICTIONARY · 4 WORKING (the
  only one edited, when Sammy says). The system registers
  copies; it does not make them.
- Notebook data backs up by export (.json). Restore is
  import. The score sheet's Test 5 (RETURN) exercises the
  full loop: delete a note, import, the note comes back.
- BACKUP/RESTORE TEST RECORD: PENDING — the loop exists
  and is specified, but a dated, recorded run of the full
  backup-and-restore test for this project has not been
  logged yet. A backup that has never been restored is an
  assumption, not a backup. The recorded run is a
  condition in gate-status-report.txt.
INCIDENTS
Prototype phase: no users, no data at risk beyond Sammy's
own device. If the prototype ever holds something it

THE REQUIREMENTS
R1 — One self-contained file: no accounts, no sign-in, no
     cloud, no external scripts, fonts, images, or network
     calls of any kind.
R2 — Opens with three notebooks: Ideas & Inspiration ·
     Sammy · Muse — Record Keeper.

     and delete notes.
R4 — Autosave to the browser's local storage on the
     device, as the user types.
R5 — One search box searches across ALL notebooks.
R6 — Export the current notebook as .txt; export
     everything as one .json; import a .json to restore.
R7 — The word PROTOTYPE stays visible in the header at
     all times.
R8 — Big buttons and big text; and no place anywhere to
     enter an API key, password, or token.
THE SIX TESTS, MAPPED
TEST 1 — MAKE
  Do: Create a new notebook, rename it, add a note, type
  in it.
  Proves: R3. Also the opening state of R2 (the three
  named notebooks are what you see first) and the working
  feel of R8 (the buttons and text you just used).
TEST 2 — SURVIVE
  Do: Close the app or file completely. Reopen it. The
  note must still be there, word for word.
  Proves: R4 — autosave that actually saves. This is the
  save war in miniature; a fail here fails the product's
  reason to exist.
TEST 3 — FIND
  Do: Put a distinctive word in a note in the SECOND
  notebook. The one search box must find it from anywhere.
  Proves: R5 — one box, all notebooks, no silos.
TEST 4 — LEAVE
  Do: Export everything as .json and one notebook as
  .txt. Both files must actually download and open.
  Proves: R6, export half — the way out works, on paper,
  not just in promise.
TEST 5 — RETURN
  Do: Delete a note. Import the .json from Test 4. The
  note must come back.
  Proves: R6, import half — export and import together are
  the bridge, and the bridge has to hold weight. This
  test doubles as the project's backup/restore test; a
  dated run of it gets logged in
  security/security-baseline.txt.
TEST 6 — ALONE
  Do: Turn off Wi-Fi and data. Reopen. Everything above
  must still work with no network.
  Proves: R1 — the whole requirement, proven the hard
  way. If it phones home, it fails the whole test, not
  just this line: our notebook answers to nobody's door
  but ours.
